# PLAN.md: Single Player Isometric RTS in Rust

This file is the authoritative plan for the repository. Every implementation, review, and remediation session must read it in full before acting, and no session may change it without the user's explicit approval recorded in `docs/DECISIONS.md`.

## 1. Purpose and scope

The goal is an original single player real time strategy game in the tradition of the classic Command & Conquer titles: a 2D isometric view with sprite graphics, base construction, ore harvesting, unit production, combat, fog of war, and skirmish matches against a computer opponent. The project is greenfield, so there is no defect or root cause to fix; the problem is the absence of the game, and the main risks are uncontrolled scope, engine API drift, and simulation logic that cannot be verified automatically. The developer works alone with a coding agent, so the work is divided into eight milestones (M0 to M7), each sized for one implement, review, and approve cycle.

Version 1.0 is a desktop executable for macOS that offers skirmish on at least three maps with two factions against an AI opponent, with a clear win and lose condition.

1. Multiplayer, networking, and replays shared between machines.
2. A scripted campaign, cutscenes, or video playback.
3. Terrain elevation, cliffs, bridges, tunnels, voxel rendering, and 3D models.
4. Naval and air units, superweapons, garrisoning, and unit veterancy in version 1.0.
5. An in game map editor (maps are authored in Tiled) and a public modding API.

## 4. Architecture

| Path | Content |
|------|---------|
| `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` | Workspace manifest, committed lock file, pinned toolchain. |
| `crates/sim/` | Library crate holding all game rules. No rendering, windowing, audio, or input dependency. |
| `crates/game/` | Binary crate holding rendering, camera, input, interface, audio, and menus. Depends on `sim`. |
| `assets/data/*.ron` | Production definitions: units, buildings, weapons, factions, AI. |
| `assets/maps/` | Map files. |
| `assets/sprites/`, `assets/audio/`, `assets/LICENSES.md` | Media and the licence record for every file not generated by this repository. |
| `crates/sim/tests/` and `crates/sim/tests/fixtures/` | Integration and end to end tests with their own fixture data and maps. |
| `docs/DECISIONS.md`, `docs/STATUS.md` | Decision log and milestone status. |

The production execution path is the same for the human player, the AI, and the tests:

1. An input source (interface in `game`, AI in `sim`, or a test) pushes an `IssuedCommand` into the `CommandQueue` resource.
2. `SimPlugin` owns a dedicated schedule, `SimSchedule`, in which one run equals exactly one simulation tick. The game runs it from Bevy's fixed timestep at 20 Hz, and tests run it directly a chosen number of times, so that tests never depend on wall clock time.
3. Within a tick the systems run in one explicitly ordered chain: command validation, AI, production and economy, pathfinding, movement, combat, death and cleanup, visibility, win condition.
4. The `game` crate reads simulation state without mutating it and draws it, interpolating positions between ticks for smooth motion.

Tests must exercise this path through `SimPlugin` and `CommandQueue`; test only shortcuts that mutate state directly are permitted only for scenario setup.

## 5. Units, equations, and data structures

| Quantity | Type and unit | Rule |
|----------|---------------|------|
| Time | `u64` tick | 20 ticks per second, 50 ms per tick. All durations in data files are in ticks. |
| Cell position | `CellPos { x: i32, y: i32 }` | Map cells, origin at cell (0, 0). |
| Fine position | `SubPos { x: i32, y: i32 }` in subcells | 256 subcells per cell; the centre of cell c is `c * 256 + 128`. |
| Speed | `u16` subcells per tick | Cells per second = speed × 20 / 256. |
| Hit points, damage | `i32` | A unit dies when hit points are ≤ 0. |
| Credits | `i64` | Never negative. |
| Power | `i32` produced and consumed | Low power when consumed > produced. |

Equations, all in integer arithmetic inside `sim`:

1. **Range check:** a target is in range when `dx² + dy² ≤ range²`, with `dx`, `dy`, and `range` in subcells and the products computed in `i64`.
2. **Damage:** `applied = base × versus[armour] / 100` with floor division, where `versus` is an integer percentage per armour class; if `versus > 0` the result is at least 1, and if `versus = 0` the result is 0.
3. **Production:** an item with cost `C` and duration `T` ticks is charged `C / T` credits on each progressing tick and the remainder `C mod T` on the final tick, so the total charged is exactly `C`. Progress pauses on any tick in which credits are insufficient. Cancelling refunds exactly the amount charged so far. Under low power, production progresses only on even ticks and defensive structures do not fire.
4. **Harvesting:** an ore cell stores an integer amount; a harvester removes a fixed amount per tick until its capacity is reached or the cell is empty, and a refinery converts the load to credits at an integer rate per ore unit.
5. **Pathfinding:** A* on the eight neighbour grid with step cost 10 orthogonal and 14 diagonal, no diagonal step between two blocked orthogonal neighbours, and the octile heuristic `h = 10 × (dx + dy) − 6 × min(dx, dy)`.
6. **Visibility:** a cell is visible to a player when some owned unit or building satisfies `dx² + dy² ≤ sight²` in cells.
7. **Projection (in `game` only, floating point allowed):** for tile width `W` and height `H` in pixels, `world_x = (cx − cy) × W / 2` and `world_y = −(cx + cy) × H / 2`; the inverse is `cx = (a + b) / 2`, `cy = (b − a) / 2` with `a = world_x / (W / 2)` and `b = −world_y / (H / 2)`, followed by floor. These formulas must be reconciled with the convention of the tilemap crate verified in M0, and the reconciled form recorded.

Core data structures in `sim`:

| Name | Kind | Purpose |
|------|------|---------|
| `SimId(u32)` | Component | Stable identifier assigned monotonically; all order sensitive iteration sorts by it. |
| `Owner(PlayerId)`, `Health`, `Armour`, `Mobile`, `Weapon`, `Harvester`, `Building`, `Producer`, `Sight` | Components | Entity state. |
| `Grid` | Resource | Per cell terrain flags (passable, buildable), ore amount, and occupant. |
| `Players` | Resource | Per player credits, power, faction, production queues, and visibility grid. |
| `Definitions` | Resource | Immutable unit, building, and weapon definitions loaded from RON. |
| `SimRng` | Resource | Seeded generator; the only source of randomness. |
| `CommandQueue` | Resource | Pending `IssuedCommand { player, command }` values. |
| `SimEvent` | Event | Includes `CommandRejected { player, command, reason }`, unit death, production complete, and match end. |

`Command` variants: `Move`, `Attack`, `AttackMove`, `Harvest`, `Stop`, `QueueProduction`, `CancelProduction`, `PlaceBuilding`, `SellBuilding`, `SetRallyPoint`. Every command is validated for ownership, existence, bounds, and visibility; an invalid command produces `CommandRejected` with a reason and changes no state.

Data files carry a `schema_version` field, are parsed with unknown fields denied and without silent defaults, and are cross validated at load (every referenced weapon, prerequisite, and sprite exists; prerequisites are acyclic). A load error names the file, the field, and the reason.

## 6. Invariants

| ID | Invariant |
|----|-----------|
| I1 | `crates/sim` has no rendering, windowing, audio, or input dependency and builds and tests headlessly. |
| I2 | Simulation state and logic use no floating point types. |
| I3 | Determinism: the same map, seed, and command sequence produce the same `state_hash` at every tick. The hash uses a hasher implemented in the crate (FNV-1a, 64 bit) over entities sorted by `SimId`. |
| I4 | Logic never depends on hash map iteration order, system ambiguity, or wall clock time. |
| I5 | The interface and the AI change simulation state only through `CommandQueue`. |
| I6 | At most one ground unit occupies a cell, and no unit occupies a cell covered by a building. |
| I7 | Credits are never negative, and the credits charged for a completed item equal its cost exactly. |
| I8 | No panic, `unwrap`, or `expect` is reachable from malformed data files or invalid commands; such inputs produce typed errors or `CommandRejected`. |
| I9 | All dependency versions are pinned exactly and `Cargo.lock` is committed. |
| I10 | Balance values live only in data files, and tests use fixture data so that balance changes do not alter test expectations. |

## 7. Milestones

Each milestone ends with a playable or runnable build, the validation commands of section 9 passing, and an independent review under section 10. The test lists are minima; section 8 defines the categories every milestone must cover.

### M0: Bootstrap and dependency verification

Scope: workspace, pinned toolchain and dependencies, `SimPlugin` with `SimSchedule`, tick counter, `CommandQueue`, `state_hash`, a `game` binary that opens a window, a `--smoke-test <frames>` flag that runs the real application for the given number of frames and exits with code 0, a spike that renders an isometric Tiled map (or the recorded fallback of A2), and `docs/DECISIONS.md` resolving A1 to A5.

Tests: the tick counter equals N after N schedule runs; two runs with the same seed and an empty command log yield equal hashes; different seeds that consume randomness yield different hashes.

Acceptance: every assumption has a recorded outcome with evidence; all versions are pinned; all validation commands pass.

### M1: Map and camera

Scope: map loading with terrain flags and ore, the `Grid` resource, map rendering, camera panning by keyboard, screen edge, and middle mouse drag, zoom with limits, camera bounds, and cursor to cell picking.

Tests: cell to world to cell round trip for every cell of 1×1, 1×N, N×1, and 64×64 maps; picking at tile centres, edges, and corners; picking outside the map returns none; malformed maps (missing layer, unknown property, zero size) return descriptive errors; camera clamping at all four borders.

Acceptance: a 64×64 demo map renders correctly, picking has zero error in tests, and the user confirms the visual result.

### M2: Units and movement

Scope: unit definitions from RON, spawning, selection by click, drag box, and additive modifier, `Move` and `Stop`, A* with a per tick request budget, cell reservation before entry, distinct destination cells for group orders, repathing when blocked, eight sprite facings, and placeholder sprites generated by the repository.

Tests: path cost is optimal on open and obstructed fixture maps; an unreachable target ends the order with an event and no panic; a move outside the map is rejected; a unit ordered to its own cell stays; a newly placed obstacle triggers a repath; I6 holds on every tick while 50 units cross each other for 2,000 ticks; determinism of the same scenario.

Acceptance: 50 units move as a group to a clicked destination without overlap or deadlock in the fixture scenarios.

### M3: Economy and construction

Scope: players, credits, power, construction yard, building and unit production queues, placement rules (buildable terrain, free footprint, within a data defined distance of an owned building), ore, the harvester cycle, refinery, rally points, and selling.

Tests: I7 for completion, pause on insufficient credits, and cancel refund; low power halves progress; placement rejections for overlap, off map, non buildable terrain, and excessive distance; a harvester with no reachable ore idles; a refinery destroyed during the return trip causes a retarget or idle state without panic; an ore cell depletes exactly to zero; integration scenario in which a scripted command sequence builds a power plant, a refinery, and a barracks and income becomes positive within a fixed tick budget.

Acceptance: a base can be built and funded from ore through commands alone.

### M4: Combat and fog of war

Scope: weapons, warheads, armour classes, instant and travelling projectiles, automatic target acquisition, `Attack` and `AttackMove`, death and cleanup, building destruction that frees cells, defensive structures, shroud and fog, and hiding of unseen enemies in rendering and in command validation.

Tests: the damage equation for every armour and warhead pair in the fixtures, including the minimum of 1 and the zero case; range at exactly `range` and at `range + 1` subcell; a target that dies while a projectile is in flight; attacks on own units, dead units, and unseen units are rejected; a destroyed unit or building releases its cells; sight radius boundary; determinism of a 20 against 20 battle.

Acceptance: two armies fight to a conclusion under fog with no panic and a stable hash across runs.

### M5: Interface and audio

Scope: sidebar with credits, power, build tabs, queue progress, and placement preview with validity colouring, minimap with fog and camera rectangle, health bars, control groups, hotkeys, pause, sound effects, music, and volume settings.

Tests: the functions that map interface actions to `Command` values are pure and unit tested for every command variant; the interface cannot obtain mutable access to simulation state (enforced by the type or module boundary); the smoke test passes with the full interface loaded.

Acceptance: a full match can be played by a human without debug shortcuts, confirmed by the user.

### M6: Skirmish AI and game flow

Scope: an AI player inside `sim` that issues commands only through `CommandQueue`, with a data defined build order, harvester management, army composition, attack waves, base defence, and rebuilding; difficulty set by data parameters; main menu, map and faction selection, win and lose detection when all buildings of a player are destroyed, end screen, and restart.

Tests: on a fixture map the AI completes its build order within a fixed tick budget; the AI issues zero rejected commands in the standard scenario; an AI with no credits and no harvester neither panics nor floods the queue; end to end AI against AI matches on every shipped map finish with a winner within a fixed tick limit, without panic, and with equal hashes across two runs.

Acceptance: the user can lose to and defeat the AI in a complete match started from the menu.

### M7: Content, balance, performance, and packaging

Scope: the second faction, the full roster, three maps, final or licensed art and audio with entries in `assets/LICENSES.md`, a balance pass, options, release builds, and a README with controls.

Tests: every production data file loads and passes cross validation; a headless benchmark with 200 moving and fighting units reports the mean and maximum tick time against the budget recorded in `docs/DECISIONS.md` (initial target: mean ≤ 5 ms in release mode on the development machine); a soak test of 36,000 ticks (30 minutes of game time) AI against AI; the release build passes the smoke test.

Acceptance: version 1.0 as defined in section 1.

## 8. Test strategy

Every milestone must include tests in each applicable category, and no existing test may be deleted, skipped, or weakened to make a change pass.

| Category | Requirement |
|----------|-------------|
| Positive | The specified behaviour occurs for valid input. |
| Negative | Invalid commands and malformed data are rejected with the specified error and no state change. |
| Boundary | Map edges, zero and maximum quantities, exact range and cost limits, empty selections. |
| Regression | Every defect found in review or play receives a test that fails before the fix and passes after it. |
| Integration | Multi system scenarios driven through `SimPlugin` and `CommandQueue` with fixture data. |
| End to end | Headless matches and the `--smoke-test` run of the real binary. |

Visual and audio behaviour that cannot be asserted automatically is verified by the user against the milestone's acceptance statement, and an agent must report such items as "requires user verification", never as passed.

## 9. Validation commands

All commands are run from the repository root, and all must exit with code 0:

```
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build --release -p game
cargo run --release -p game -- --smoke-test 600
cargo run -p game -- --smoke-test 600
```

If the environment has no display, the last command is reported as "not executed, no display" and left for the user. From M7 the benchmark and soak commands defined in that milestone are added.

## 10. Workflow, roles, and gates

Roles are separated: the implementer is one agent session, the reviewer is a different and independent session (preferably a different model) that did not write the code, and the user is the approver. The implementer is never the sole approver.

The cycle for each milestone is:

1. **Implement** on branch `milestone/mN`, in small coherent commits, after inspecting the repository and verifying every path, symbol, crate API, and assumption against current evidence. Changes are limited to the milestone scope, with no unrelated refactoring.
2. **Report** with: files changed; each validation command with its exit status and test counts; a table of acceptance criteria with evidence for each; assumptions verified and how; deviations from this plan; known debt. `docs/STATUS.md` is updated.
3. **Independent review** of the complete cumulative diff since the tag of the last approved milestone, covering runtime execution of the production path, error context, silent fallbacks or data loss, API and schema changes, test adequacy, numerical correctness against section 5, the invariants of section 6, and regressions. The reviewer reruns the validation commands.
4. **Remediation** in a new implementer session, in which each review finding is treated as a claim to be reconciled against the current code before it is fixed or refuted with evidence.
5. **Re-review** by an independent session, then approval by the user and tag `mN-approved`.

Severity: **P0** is a crash, data loss, broken build, violated invariant, or incorrect simulation result; **P1** is a missing acceptance criterion, inadequate test for specified behaviour, silent fallback, or unverified assumption; **P2** is maintainability, naming, or documentation debt.

Decisions: **GO**; **GO WITH DOCUMENTED NON-BLOCKING DEBT** (only P2 items, each recorded in `docs/STATUS.md`); **NO-GO**, which is mandatory for any unresolved P0 or P1, failed validation command, unverified acceptance criterion, unresolved numerical or data integrity risk, or broken compatibility.

Compatibility rules: dependency or toolchain upgrades happen only in a dedicated change with a decision record; a data schema change increments `schema_version` and updates all data files and fixtures in the same change.

## 11. Failure conditions

A milestone fails, and work stops for user input, when any of the following holds: a validation command fails; an invariant of section 6 is violated; a test was removed, skipped, or weakened; `sim` gained a forbidden dependency; an assumption of section 2 proved false and no recorded fallback applies; the plan appears wrong or contradictory; or third party material without a recorded licence entered the repository. In these cases the agent reports the evidence and proposes options instead of improvising beyond the plan.

## 12. Orchestrated workflow and amendments

1. An orchestrator session may run the cycle of section 10 automatically, using a separate subagent with a fresh context for each implementation, review, and remediation step. A reviewer subagent must never have implemented or remediated the code it reviews, and its decision is binding on the orchestrator. After GO or GO WITH DOCUMENTED NON-BLOCKING DEBT the orchestrator merges the milestone branch, creates the tag `mN-reviewed`, and proceeds without waiting for the user. The cumulative diff for a review is taken from the most recent `mN-reviewed` or `mN-approved` tag.
2. Acceptance items that only the user can verify (visual and audio behaviour) are listed in docs/STATUS.md under "requires user verification". They are not review findings, never justify NO-GO, and block only the tag `mN-approved`, which the user alone creates.
3. Version 1.0 targets macOS only.
4. Invariant I11: every external file handed to a third party parser or renderer is restricted to an explicitly listed supported subset, and anything outside that subset is rejected with a typed error before the hand off, either by reading the input with the same rules as the third party code or by checking the parsed result. Invariant I12: simulation arithmetic that can overflow uses explicit checked, saturating, or wrapping operations, so that debug and release builds behave identically.
5. Section 9 gains the command `cargo run -p game -- --smoke-test 600` (debug profile).

Where this section conflicts with sections 1 to 11, this section prevails.

are accepted by the user. Collecting Rust-crate notices is not a user-requested release criterion;
existing asset/font notices remain. These decisions do not change dependency licences.
